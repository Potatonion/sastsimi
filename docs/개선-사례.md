# 개선 사례

| 사례 | 문제와 확인 방법 | 개선 후 보여줄 결과 |
| --- | --- | --- |
| 복구 판단이 시간 안에 끝나지 않음 | 재시도 여부만 판단하는 호출인데 제한이 2분이라 답을 받기 전에 끊겼다. 진행 기록에서 복구 단계가 시간 초과로 멈추고, 가설이 판단 없이 중단된 것으로 확인했다. | 복구 판단 제한은 5분이다. 복구 모델은 grok-4.7-high-fast다. 호출 제한을 이미 다 쓴 경우, Docker가 없는 경우, 컨테이너에 파일을 넣지 못한 경우는 모델을 다시 부르지 않고 멈춘다. 실행이 중간에 끊긴 경우는 같은 단계를 다시 연다. |
| 실행 실패마다 PoC 계획을 다시 세움 | 계획을 세우고 후보를 만든 뒤 실행이 실패하면, 복구 때 계획부터 다시 세우고 후보도 다시 만들었다. 실행 복구 기록이 후보 생성 단계로 돌아가 같은 계획이 반복된 것으로 확인했다. | 처음에는 계획을 세운 뒤 스크립트를 만든다. 기술 게이트의 수정 요청이 없는 실행 복구는 저장된 계획을 다시 쓰고, 실패한 실행을 반영해 스크립트만 다시 만든다. 게이트가 수정을 요청하면 계획을 다시 세운다. |
| 닫히지 않은 문제가 가설에서 빠짐 | 사실이 그럴듯해도 증거가 완전히 닫히기 전에는 가설로 잘 들어가지 않았다. 개수를 채우거나 상한을 없애는 방식은 쓰지 않았다. 의도된 취약 환경에서 저장된 가설 수가 서로 다른 문제보다 적게 남은 것으로 확인했다. | 상한 64는 폭주를 막는 값으로 둔다. 서로 다른 문제마다, 증거가 닫히지 않아도 사실로 그럴듯하면 가설 하나를 만든다. 없는 코드를 만들지 않고, 같은 문제나 빈 가설은 넣지 않는다. 재현, 게이트, 보고서 기준은 그대로다. FALSE와 미결은 보고서로 올리지 않는다. |
| 보고서 재시도가 전달 한도를 넘음 | 초안이 스키마를 통과하지 못하면 같은 스키마를 프롬프트에 한 번 더 붙였다. 그 덩어리가 한 인자 한도를 넘으면 재시도가 바로 실패했다. A-010 가설 f881에서 1차는 CURSOR_INVALID_OUTPUT, 2차는 18ms 만에 CURSOR_PROMPT_TOO_LARGE였고, 보고서 단계는 재시도 불가로 남았다. | 스키마는 첫 프롬프트에만 둔다. 재시도는 이미 준 스키마에 맞추라는 짧은 수정 지시만 붙인다. 문자열이 닫히지 않은 상태면 닫는 따옴표를 앞에 붙여 다음 줄에서 나눌 수 있게 한다. 인자 한도 96KB는 그대로다. 이미 실패로 닫힌 f881 보고서는 자동으로 다시 열리지 않는다. |
| 보고서 문안 검사가 예외로 중단됨 | 버전, CVSS, 심각도, 공개 가능 같은 문안은 거절되는데, 그 거절이 예외로 새어 STAGE_UNEXPECTED_ERROR가 됐다. 복구는 원인을 모른 채 한 번 재시도한 뒤 STOP했다. A-010 가설 e51의 보고서 기록과, 저장된 초안을 같은 검사에 다시 넣어 REPORT_UNSUPPORTED_METADATA_CLAIM이 난 것으로 확인했다. | 그 검사는 최대 3번까지 같은 스키마로 고친 초안을 다시 받는다. 버전 번호, CVSS, 심각도, 공개 판단, 확인되지 않은 코드 위치는 빼라고 지시한다. 그래도 실패하면 그 오류 코드로 보고서 단계를 다시 연다. e51은 재개 후 보고서가 저장됐다. |
| 선택된 모델 때문에 한 호출이 길어짐 | PoC 후보 생성이 grok-4.7-xhigh로 10분 넘게 대기했다. 진행 줄의 모델 이름과 호출 시간으로 확인했다. | 기본 모델과 선택된 에이전트 모델은 grok-4.7-high-fast다. 설정은 프로세스를 다시 켤 때 적용된다. A-010 재개 진행 줄에 poc_candidate / grok-4.7-high-fast가 표시됐다. |
